# v0.2.10 — Durable Runtime Trace Ledger

Status: **WAVE 13 CANDIDATE / STACKED ON RELEASE AUTHORITY PR #20**

## Durable run identity

SQLiteRuntimeTraceLedger binds each `run_id` to an
`ExecutionSpecV2` fingerprint. Re-registering the same run/spec is
idempotent; binding the same run id to different spec content fails closed.

The fingerprint covers runtime-relevant request, objective, complexity,
capabilities, patterns, execution nodes, artifacts, gates, failure routes and
output contract.

## Hash-chained provenance events

Runtime events are persisted in SQLite with:

- per-run event index;
- event type;
- node/artifact identity;
- from/to state;
- reason/details;
- timezone-aware timestamp;
- previous event hash;
- event hash.

`verify_chain(run_id)` recomputes the chain and detects row tampering.

This is an integrity chain, not a cryptographic signature against a malicious
database owner.

## Artifact metadata

The ledger persists artifact metadata only:

- artifact id/type;
- producer node;
- SHA-256;
- byte size;
- validation state;
- artifact sequence.

Artifact bytes are not stored.

Identical metadata is idempotent; conflicting metadata for the same run and
artifact id fails closed.

## RuntimeStateMachine integration

Tracing is optional. Existing in-process behavior is unchanged when no ledger
is supplied.

When a ledger is supplied:

- runtime initialization is committed;
- node start is committed before READY→RUNNING mutation;
- artifact metadata + PASS + dependent READY events are committed in one
  ledger step before in-memory PASS mutation;
- node failure + downstream BLOCKED events are committed together before
  in-memory failure mutation;
- trace-write failure prevents the corresponding state transition.

## Scope limit

This wave provides durable audit/provenance evidence. It does **not** yet
provide:

- automatic runtime reconstruction;
- resume/replay after process crash;
- distributed locking;
- multi-worker consensus;
- exactly-once execution.
