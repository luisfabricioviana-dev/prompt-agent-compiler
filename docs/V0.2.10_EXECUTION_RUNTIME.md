# v0.2.10 — Execution Runtime Contracts

Status: **WAVE 1 CANDIDATE / STACKED ON RECONCILIATION PR #7**

## Purpose

Wave 1 turns previously descriptive compiler outputs into runtime-checkable
contracts without changing the recovered semantic/policy lineage or enabling
REA publication.

## CapabilityRegistry

Runtime capability states are explicit:

- `AVAILABLE`
- `CONSTRAINED`
- `UNAVAILABLE`
- `UNKNOWN`

Missing registrations remain `UNKNOWN`. They are never silently treated as
available.

Required-capability resolution produces one of:

- `READY`
- `ADAPT_REQUIRED`
- `UNKNOWN`
- `BLOCKED`

Optional unavailable capabilities are recorded but do not block execution.

## ExecutionSpecV2

The new contract adds executable structure:

- objective and success definition;
- capability resolution;
- execution nodes and prerequisites;
- artifact contracts;
- quality gates;
- verification plan;
- failure routes;
- stop conditions;
- output contract;
- learning trace;
- compatibility fields for recovered v0.2.9 routing.

Readiness is derived from validation plus capability state:

- `READY`
- `ADAPT_REQUIRED`
- `UNKNOWN_CAPABILITY`
- `BLOCKED`
- `INVALID`

The graph validator rejects missing prerequisites, dependency cycles, missing
artifact producers/consumers, unresolved node capabilities and invalid failure
route sources.

## Compatibility

`ExecutionSpecV2.from_legacy(...)` preserves the recovered request,
complexity, constraints, contradictions, patterns and quality gates while
requiring the caller to declare which capability labels are mandatory.

This is an adapter, not a claim that v0.2.9 has already been migrated to the
new runtime.

## Safety boundary

This wave does **not**:

- enable REA dispatch;
- select or call a semantic model;
- change holdout or promotion criteria;
- infer capability availability from task wording;
- treat `UNKNOWN` capability state as `AVAILABLE`.
